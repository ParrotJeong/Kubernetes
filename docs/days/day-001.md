# Day 1 · 클러스터 아키텍처와 Pod

## 오늘의 목표

- kubeadm 클러스터에서 컨트롤 플레인 구성요소가 **static Pod** 로 실행된다는 것을 직접 확인한다.
- `kubectl run` 과 `--dry-run=client -o yaml` 로 Pod 를 빠르게 만든다.
- Pod 에서 **실행 중에 바꿀 수 있는 필드와 없는 필드**를 구분하고, 바꿀 수 없는 필드는 다시 만들어서 고친다.
- kubectl 없이 노드에서 `crictl` 로 컨테이너를 확인한다.

## Q1. 컨트롤 플레인 구성요소 조사
<!-- domain: cluster | level: 1 | minutes: 5 -->

**작업 노드**: `controlplane`

> **Task**
>
> 1. Write the full image name (including the tag) of the etcd Pod to `/opt/day01/etcd-image.txt`.
> 2. Write the directory from which the kubelet on `controlplane` loads static Pod manifests to `/opt/day01/static-path.txt`.
> 3. Write the names of all static Pods in the `kube-system` namespace to `/opt/day01/static-pods.txt`, one name per line.

**한국어 요약**: etcd Pod 의 이미지(태그 포함), kubelet 이 static Pod 매니페스트를 읽는 디렉터리, `kube-system` 의 static Pod 이름 목록을 각각 파일로 저장하세요.

📖 참고 문서: [Create static Pods](https://kubernetes.io/docs/tasks/configure-pod-container/static-pod/) · [JSONPath Support](https://kubernetes.io/docs/reference/kubectl/jsonpath/)

<details>
<summary>힌트</summary>

- kubelet 이 어떤 설정 파일을 쓰는지는 `ps aux | grep kubelet` 의 `--config` 플래그로 알 수 있습니다.
- static Pod 는 kubelet 이 직접 만들기 때문에, API 서버에 보이는 Pod 의 소유자(`ownerReferences`)가 **Node** 입니다.

</details>

<details>
<summary>정답 및 해설</summary>

```bash
# 1) etcd 이미지
kubectl -n kube-system get pod -l component=etcd \
  -o jsonpath='{.items[0].spec.containers[0].image}' > /opt/day01/etcd-image.txt

# 2) kubelet 설정 파일 → staticPodPath
ps aux | grep kubelet | grep -o -- '--config=[^ ]*'    # --config=/var/lib/kubelet/config.yaml
grep staticPodPath /var/lib/kubelet/config.yaml         # staticPodPath: /etc/kubernetes/manifests
echo /etc/kubernetes/manifests > /opt/day01/static-path.txt

# 3) 소유자가 Node 인 Pod = static Pod
kubectl -n kube-system get pods \
  -o custom-columns=NAME:.metadata.name,OWNER:.metadata.ownerReferences[0].kind
kubectl -n kube-system get pods \
  -o jsonpath='{range .items[?(@.metadata.ownerReferences[0].kind=="Node")]}{.metadata.name}{"\n"}{end}' \
  > /opt/day01/static-pods.txt
```

**확인**

```bash
cat /opt/day01/etcd-image.txt /opt/day01/static-path.txt /opt/day01/static-pods.txt
ls /etc/kubernetes/manifests   # etcd.yaml  kube-apiserver.yaml  kube-controller-manager.yaml  kube-scheduler.yaml
```

**해설**

- kubeadm 은 etcd, kube-apiserver, kube-controller-manager, kube-scheduler 를 `/etc/kubernetes/manifests/` 의 YAML 로 띄웁니다. kubelet 이 이 디렉터리를 지켜보다가 파일이 생기면 Pod 를 만들고, 고치면 다시 만들고, 지우면 없앱니다. **컨트롤 플레인 장애 문제 대부분이 이 파일을 고치는 문제**입니다.
- API 서버에 보이는 것은 kubelet 이 대신 등록한 *미러 Pod* 라서 `kubectl delete` 로 지워도 곧바로 다시 생깁니다. 이름이 `<구성요소>-<노드이름>` 형태(예: `etcd-controlplane`)인 것도 특징입니다.
- custom-columns 의 OWNER 열을 보면 kube-proxy 는 `DaemonSet`, coredns 는 `ReplicaSet` 소유라는 것도 함께 확인할 수 있습니다.
- 출력 파일 문제는 경로나 형식이 틀리면 점수를 받지 못합니다. 저장한 뒤 `cat` 으로 꼭 확인하세요.

</details>

## Q2. 명령형으로 Pod 만들기
<!-- domain: workloads | level: 1 | minutes: 3 -->

**작업 노드**: `controlplane`

> **Task**
>
> Create a Pod named `web` in the namespace `day01` using the image `nginx:1.29-alpine`.
> The Pod must have the labels `app=web` and `tier=frontend`, and its container must expose port `80`.

**한국어 요약**: `day01` 네임스페이스에 `nginx:1.29-alpine` 이미지로 `web` Pod 를 만들고, 라벨 두 개와 컨테이너 포트 80 을 지정하세요.

📖 참고 문서: [kubectl Quick Reference](https://kubernetes.io/docs/reference/kubectl/quick-reference/)

<details>
<summary>힌트</summary>

`kubectl run --help` 에서 `--labels` 와 `--port` 옵션을 찾아보세요.

</details>

<details>
<summary>정답 및 해설</summary>

```bash
kubectl -n day01 run web --image=nginx:1.29-alpine --labels=app=web,tier=frontend --port=80
```

**확인**

```bash
kubectl -n day01 get pod web -o wide --show-labels
kubectl -n day01 get pod web -o jsonpath='{.spec.containers[0].ports}{"\n"}'   # [{"containerPort":80,"protocol":"TCP"}]
```

**해설**

- `kubectl run` 은 Pod 하나를 만드는 가장 빠른 방법입니다. 라벨을 주지 않으면 `run=web` 라벨이 붙고, `--labels` 를 쓰면 지정한 라벨만 붙습니다.
- `--port` 는 `containerPort` 를 기록할 뿐 Service 를 만들지는 않습니다. `--expose` 를 함께 주면 같은 이름의 ClusterIP Service 도 만들어집니다(Day 2 에서 다룹니다).
- 시험에서 가장 흔한 실수는 `-n` 을 빠뜨려 `default` 네임스페이스에 만드는 것입니다.

</details>

## Q3. dry-run YAML 로 컨테이너 2개짜리 Pod 만들기
<!-- domain: workloads | level: 2 | minutes: 7 -->

**작업 노드**: `controlplane`

> **Task**
>
> Generate a manifest for a Pod named `toolbox` in the namespace `day01` **without creating the Pod**, and save it to `/opt/day01/toolbox.yaml`.
> Edit the file so that the Pod has exactly two containers:
>
> - `main`: image `busybox:1.37`, runs the command `sleep 3600`
> - `helper`: image `nginx:1.29-alpine`
>
> Then create the Pod from the file. Both containers must be running.

**한국어 요약**: Pod 를 만들지 않은 채 `toolbox` Pod 의 YAML 을 `/opt/day01/toolbox.yaml` 로 저장하고, 컨테이너 2개(`main`, `helper`)를 갖도록 고친 다음 그 파일로 생성하세요.

📖 참고 문서: [Pods](https://kubernetes.io/docs/concepts/workloads/pods/) · [Define a Command and Arguments for a Container](https://kubernetes.io/docs/tasks/inject-data-application/define-command-argument-container/)

<details>
<summary>힌트</summary>

- `--dry-run=client -o yaml` 은 서버에 보내지 않고 YAML 만 출력합니다.
- `--command --` 뒤에 쓴 값은 `command` 필드가 됩니다.

</details>

<details>
<summary>정답 및 해설</summary>

```bash
kubectl -n day01 run toolbox --image=busybox:1.37 \
  --dry-run=client -o yaml --command -- sleep 3600 > /opt/day01/toolbox.yaml
vi /opt/day01/toolbox.yaml
```

```yaml
apiVersion: v1
kind: Pod
metadata:
  labels:
    run: toolbox
  name: toolbox
  namespace: day01
spec:
  containers:
  - name: main              # toolbox → main 으로 이름 변경
    image: busybox:1.37
    command:
    - sleep
    - "3600"
  - name: helper            # 두 번째 컨테이너 추가
    image: nginx:1.29-alpine
  restartPolicy: Always
```

```bash
kubectl apply -f /opt/day01/toolbox.yaml
```

**확인**

```bash
kubectl -n day01 get pod toolbox    # READY 2/2, STATUS Running
kubectl -n day01 get pod toolbox -o jsonpath='{range .spec.containers[*]}{.name}{"\t"}{.image}{"\n"}{end}'
```

**해설**

- `export do="--dry-run=client -o yaml"` 을 만들어 두면 `k run toolbox --image=busybox:1.37 $do --command -- sleep 3600` 처럼 짧게 쓸 수 있습니다.
- busybox 는 실행할 명령이 없으면 바로 끝나서 `CrashLoopBackOff` 가 됩니다. 그래서 `sleep` 처럼 오래 도는 명령을 줍니다.
- `"3600"` 을 따옴표로 감싸는 이유: `command` 는 문자열 배열인데 따옴표가 없으면 YAML 이 숫자로 읽어서 생성할 때 오류가 납니다.
- dry-run 이 넣어 준 `resources: {}`, `dnsPolicy`, `status: {}` 같은 줄은 지워도 되고 남겨도 됩니다.
- READY 가 `1/2` 면 `kubectl -n day01 describe pod toolbox` 의 Events 와 `kubectl -n day01 logs toolbox -c main` 으로 어느 컨테이너가 문제인지 봅니다. 컨테이너가 여러 개인 Pod 에서는 `logs` 에 `-c` 로 컨테이너를 지정합니다.

</details>

## Q4. 실행되지 않는 Pod 고치기
<!-- domain: troubleshooting | level: 2 | minutes: 7 -->

**작업 노드**: `controlplane`

**사전 준비** (먼저 실행해서 고장 난 상태를 만드세요)

```bash
kubectl -n day01 run broken --image=redis:7.4-alpinee --labels=app=broken
```

> **Task**
>
> The Pod `broken` in the namespace `day01` is not running. Find out why and fix it:
>
> - The Pod must run the image `redis:7.4-alpine`.
> - Its container must declare the container port `6379`.
> - Keep the Pod name and its existing labels.

**한국어 요약**: `broken` Pod 가 실행되지 않는 원인을 찾아, `redis:7.4-alpine` 이미지로 실행되고 컨테이너 포트 6379 를 갖도록 고치세요. 이름과 기존 라벨은 그대로 둡니다.

📖 참고 문서: [Debug Pods](https://kubernetes.io/docs/tasks/debug/debug-application/debug-pods/)

<details>
<summary>힌트</summary>

- `kubectl describe pod` 의 **Events** 와 컨테이너의 **State / Reason** 을 보세요.
- 실행 중인 Pod 에서 바꿀 수 있는 필드는 몇 개 되지 않습니다. 바꿀 수 없는 필드는 어떻게 고칠까요?

</details>

<details>
<summary>정답 및 해설</summary>

```bash
# 1) 원인 확인
kubectl -n day01 get pod broken                      # STATUS: ErrImagePull 또는 ImagePullBackOff
kubectl -n day01 describe pod broken | tail -n 15    # Failed to pull image "redis:7.4-alpinee" ... not found

# 2) 이미지는 실행 중에도 바꿀 수 있는 필드
kubectl -n day01 set image pod/broken broken=redis:7.4-alpine

# 3) 포트 추가는 바꿀 수 없는 필드 → YAML 로 저장해 고친 뒤 다시 만든다
kubectl -n day01 get pod broken -o yaml > /opt/day01/broken.yaml
vi /opt/day01/broken.yaml      # 아래처럼 containers[0] 에 ports 추가
```

```yaml
spec:
  containers:
  - image: redis:7.4-alpine
    name: broken
    ports:
    - containerPort: 6379
```

```bash
kubectl replace --force -f /opt/day01/broken.yaml    # 지우고 같은 이름으로 다시 생성
```

**확인**

```bash
kubectl -n day01 get pod broken --show-labels        # Running, app=broken
kubectl -n day01 get pod broken \
  -o jsonpath='{.spec.containers[0].image} {.spec.containers[0].ports[0].containerPort}{"\n"}'
```

**해설**

- 이미지 태그 오타(`alpinee`) 때문에 이미지를 받지 못해 `ErrImagePull` → `ImagePullBackOff` 상태가 됩니다. 이미지 문제는 `describe` 의 Events 에 원인이 그대로 나옵니다.
- 실행 중인 Pod 에서 바꿀 수 있는 것은 `image`, `activeDeadlineSeconds`, `tolerations`(추가만) 같은 일부 필드뿐입니다. 포트를 바꾸려고 하면 이런 오류가 납니다.

  ```text
  The Pod "broken" is invalid: spec: Forbidden: pod updates may not change fields other than
  `spec.containers[*].image`,`spec.initContainers[*].image`,`spec.activeDeadlineSeconds`,`spec.tolerations` ...
  ```

- `kubectl edit pod broken` 으로 고쳐도 같은 오류가 나는데, 이때 kubectl 이 수정한 내용을 `/tmp/kubectl-edit-xxxx.yaml` 로 저장해 줍니다. 그 파일로 `kubectl replace --force -f /tmp/kubectl-edit-xxxx.yaml` 하면 됩니다. 시험에서 가장 자주 쓰는 패턴입니다.
- 이미지와 포트를 YAML 에서 한 번에 고치고 `replace --force` 한 번만 해도 정답입니다.

</details>

## Q5. crictl 로 노드에서 컨테이너 확인하기
<!-- domain: troubleshooting | level: 2 | minutes: 6 -->

**작업 노드**: `controlplane` → Pod `web` 이 실행 중인 노드

> **Task**
>
> 1. Write the name of the node on which the Pod `web` (namespace `day01`) is running to `/opt/day01/web-node.txt` on `controlplane`.
> 2. Connect to that node. **Without using kubectl**, use the container runtime CLI to find the container of the Pod `web`, and:
>    - write its container ID to `/opt/day01/web-container-id.txt`
>    - write its logs (both stdout and stderr) to `/opt/day01/web.log`
>
>    Both files must be created on that node.

**한국어 요약**: `web` Pod 가 실행 중인 노드 이름을 파일로 저장하고, 그 노드에 접속해 kubectl 없이 `crictl` 로 컨테이너 ID 와 로그(stdout, stderr 모두)를 그 노드의 파일로 저장하세요.

📖 참고 문서: [Debugging Kubernetes nodes with crictl](https://kubernetes.io/docs/tasks/debug/debug-cluster/crictl/)

<details>
<summary>힌트</summary>

- 노드 이름은 `kubectl get pod -o wide` 의 NODE 열에 있습니다.
- `crictl ps` 는 `--name` 으로 컨테이너 이름을 거를 수 있고, `-q` 를 붙이면 ID 만 출력합니다.
- stderr 까지 파일로 보내려면 리다이렉션을 어떻게 써야 할까요?

</details>

<details>
<summary>정답 및 해설</summary>

```bash
# controlplane 에서
kubectl -n day01 get pod web -o jsonpath='{.spec.nodeName}' > /opt/day01/web-node.txt
cat /opt/day01/web-node.txt        # 예: node01

ssh node01                         # 위에서 확인한 노드로 접속
mkdir -p /opt/day01
crictl pods --name web             # Pod 샌드박스 확인
crictl ps --name web               # 컨테이너 확인
crictl ps --name web -q > /opt/day01/web-container-id.txt
crictl logs "$(cat /opt/day01/web-container-id.txt)" > /opt/day01/web.log 2>&1
exit                               # controlplane 으로 돌아오기
```

**확인**

```bash
ssh node01 'cat /opt/day01/web-container-id.txt; wc -l /opt/day01/web.log'
```

**해설**

- Pod 가 실행되는 흐름: kubectl → API 서버 → 스케줄러가 노드 배정 → 그 노드의 kubelet → CRI(containerd)가 컨테이너 실행. `crictl` 은 CRI 에 직접 붙는 도구라서 **API 서버가 죽어 kubectl 이 안 될 때**도 컨테이너 상태와 로그를 볼 수 있습니다. 컨트롤 플레인 장애 문제의 기본 도구입니다.
- `crictl logs` 는 컨테이너의 stdout 과 stderr 를 나눠서 그대로 내보냅니다. nginx 는 시작 메시지를 stderr 로 쓰기 때문에 `2>&1` 이 없으면 로그 일부가 파일에서 빠집니다. (`kubectl logs` 는 두 스트림을 합쳐서 보여줍니다.)
- `--name` 은 정규식이라 이름에 `web` 이 들어간 다른 컨테이너도 걸릴 수 있습니다. 정확히 고르려면 `crictl ps --name '^web$' --label io.kubernetes.pod.namespace=day01` 처럼 좁힙니다.
- 시험에서는 작업을 마치면 꼭 `exit` 로 원래 호스트에 돌아오세요. 그래야 다음 문제의 `ssh` 가 정상 동작합니다.

</details>

## ✅ 오늘의 정리

| 상황 | 명령 |
| --- | --- |
| Pod 빠르게 만들기 | `k run <이름> --image=<이미지> --labels=k=v --port=80 -n <ns>` |
| YAML 뼈대 만들기 | `k run <이름> --image=<이미지> --dry-run=client -o yaml > pod.yaml` |
| 실행 명령 지정 | `k run ... --command -- sleep 3600` |
| 이미지만 바꾸기 | `k set image pod/<이름> <컨테이너>=<이미지>` |
| 바꿀 수 없는 필드 고치기 | `k get pod <이름> -o yaml > p.yaml` → 수정 → `k replace --force -f p.yaml` |
