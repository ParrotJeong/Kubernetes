## 🗺️ 한눈에 보기

```text
  kubectl / users
      | HTTPS :6443
      v
+---------------- Control plane (controlplane) ----------------+
| kube-apiserver <--> etcd  (:2379 client / :2380 peer)        |
|    ^      ^                                                  |
|    |      +-- kube-controller-manager (:10257)               |
|    +--------- kube-scheduler          (:10259)               |
+--------------------------------------------------------------+
      |  watch Pod specs (v)      (^) report status
+-------------------- Worker node (node01) --------------------+
| kubelet (:10250) --CRI gRPC--> containerd --> containers     |
| kube-proxy (:10256) --> iptables / nftables (Services)       |
+--------------------------------------------------------------+
```

클러스터는 **컨트롤 플레인**(두뇌)과 **워커 노드**(일꾼)로 나뉩니다. 강의의 비유로는 워커 노드가 컨테이너를 싣고 다니는 화물선, 컨트롤 플레인이 화물선들을 계획·감시·조정하는 관제선입니다.

| 구성요소 | 위치 | 하는 일 | kubeadm 실행 방식 | 포트 |
| --- | --- | --- | --- | --- |
| kube-apiserver | 컨트롤 플레인 | Kubernetes API 제공. 인증·인가·어드미션 후 etcd 에 읽고 씀 | static Pod | 6443 |
| etcd | 컨트롤 플레인 | 클러스터 상태를 저장하는 키-값 DB | static Pod | 2379, 2380 |
| kube-scheduler | 컨트롤 플레인 | 노드가 정해지지 않은 Pod 에 노드를 골라 줌 | static Pod | 10259 |
| kube-controller-manager | 컨트롤 플레인 | 컨트롤러(감시 → 비교 → 조치 루프) 모음 | static Pod | 10257 |
| cloud-controller-manager | 컨트롤 플레인 (선택) | 클라우드 API 연동 | 클라우드에서만 | — |
| kubelet | 모든 노드 | 노드 등록, Pod 실행·감시, 상태 보고 | **systemd 서비스** | 10250 |
| kube-proxy | 모든 노드 (선택) | Service IP → Pod IP 전달 규칙 | DaemonSet | 10256 |
| 컨테이너 런타임 | 모든 노드 | 이미지를 받아 컨테이너 실행 | systemd 서비스 (containerd) | — |
| CoreDNS (애드온) | — | 클러스터 DNS | Deployment | 53 |

## 1. Pod 하나가 실행되기까지

1. **kubectl → kube-apiserver**: 요청은 인증(누구인가) → 인가(권한이 있나, RBAC) → 어드미션(정책 검사, 기본값 채우기)을 거쳐 etcd 에 저장됩니다. 이때 Pod 의 `spec.nodeName` 은 비어 있습니다.
2. **kube-scheduler**: API 서버를 지켜보다가(watch) 노드가 없는 Pod 를 발견하면 노드를 고르고, API 서버를 통해 `spec.nodeName` 을 기록합니다(바인딩).
3. **kubelet**: 자기 노드에 배정된 Pod 를 발견하면 CRI 로 containerd 에 컨테이너 생성을 요청합니다.
4. **kubelet → kube-apiserver**: Pod 상태(Running, IP 등)를 보고하고, API 서버가 etcd 에 저장합니다.

Deployment 로 만들면 앞에 컨트롤러가 끼어듭니다. Deployment 컨트롤러가 ReplicaSet 을, ReplicaSet 컨트롤러가 Pod 를 만듭니다(Day 2).

> 🎯 **모든 구성요소는 kube-apiserver 를 통해서만 대화하고, etcd 에 직접 접근하는 것은 API 서버뿐입니다.** 그래서 API 서버가 죽으면 `kubectl` 이 전부 안 되고, 이때는 노드에서 `crictl` 로 컨테이너를 봐야 합니다.

구성요소가 고장 나면 이런 증상이 납니다. 트러블슈팅 문제(시험 비중 30%)의 출발점입니다.

| 고장 난 구성요소 | 보이는 증상 |
| --- | --- |
| kube-apiserver | `kubectl` 이 `connection refused` (6443) |
| etcd | API 서버도 같이 비정상 → `kubectl` 오류·타임아웃 |
| kube-scheduler | 새 Pod 가 계속 `Pending`, 노드가 비어 있고 Events 도 없음 |
| kube-controller-manager | Deployment 를 만들어도 Pod 가 안 생김, scale 이 반영 안 됨 |
| kubelet | 노드가 `NotReady`, 그 노드의 Pod 상태가 갱신되지 않음 |
| kube-proxy | Service IP 로는 접속이 안 되는데 Pod IP 로는 됨 |

## 2. 컨트롤 플레인 구성요소

### kube-apiserver

- 클러스터의 정문입니다. kubectl, 컨트롤러, 스케줄러, kubelet 이 모두 API 서버와만 통신합니다.
- 여러 대로 늘려 로드밸런서 뒤에 둘 수 있습니다(수평 확장). 고가용성 구성은 Day 26 에서 다룹니다.
- kubeadm 에서는 `/etc/kubernetes/manifests/kube-apiserver.yaml` 의 static Pod 입니다. 실제 옵션은 `ps aux | grep kube-apiserver` 로도 볼 수 있습니다.

| 자주 보는 플래그 | 의미 |
| --- | --- |
| `--etcd-servers` | 접속할 etcd 주소 (예: `https://127.0.0.1:2379`) |
| `--etcd-cafile`, `--etcd-certfile`, `--etcd-keyfile` | etcd 에 접속할 때 쓰는 인증서 |
| `--client-ca-file` | 클라이언트 인증서를 검증하는 CA |
| `--tls-cert-file`, `--tls-private-key-file` | API 서버 자신의 서버 인증서 |
| `--authorization-mode` | 인가 방식 (kubeadm 기본 `Node,RBAC`) |
| `--enable-admission-plugins` | 켤 어드미션 플러그인 (Day 6) |
| `--service-cluster-ip-range` | Service ClusterIP 대역 (Day 23) |

`kubectl get --raw /api/v1/namespaces/default/pods` 를 쓰면 kubectl 이 인증을 대신 처리해 주므로 REST API 응답을 그대로 볼 수 있습니다. 강의의 `curl -k ... https://127.0.0.1:6443/api/v1/...` 예시와 같은 API 입니다.

### etcd

- 클러스터의 모든 데이터를 담는 일관성 있는 고가용성 키-값 저장소입니다. 유일한 진실 원천이라 잃으면 클러스터를 되살릴 수 없습니다. 백업과 복구는 Day 14 에서 다룹니다.
- 리소스는 `/registry` 아래에 저장됩니다. 예: `/registry/pods/day01/web`
- 포트: **2379** 는 클라이언트용(API 서버가 접속), **2380** 은 피어용(etcd 멤버끼리).
- kubeadm 에서는 static Pod 이고, 데이터는 노드의 `/var/lib/etcd`, 인증서는 `/etc/kubernetes/pki/etcd/` 에 있습니다.
- 바이너리와 systemd 로 직접 설치한 클러스터도 있으니, 시험에서 etcd 설정을 찾을 때는 static Pod 매니페스트와 `ps aux | grep etcd` 를 둘 다 확인하세요.

```bash
# kubeadm 클러스터에서 etcd 에 저장된 Pod 키 보기 (TLS 인증서 필요)
kubectl -n kube-system exec etcd-controlplane -- etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  get /registry/pods --prefix --keys-only
```

> ⚠️ **최신 버전**: etcd 3.4 부터 `etcdctl` 은 v3 API 가 기본이라 `ETCDCTL_API=3` 을 붙이지 않아도 됩니다. 강의의 `etcdctl get "" --prefix --keys-only` 는 TLS 를 쓰는 kubeadm 클러스터에서는 위처럼 인증서 옵션을 붙여야 동작합니다.

### kube-scheduler

- 노드가 정해지지 않은 Pod 를 찾아 **어느 노드에서 실행할지 결정만** 합니다. 컨테이너를 실제로 띄우는 것은 그 노드의 kubelet 입니다.
- 결정은 두 단계입니다.
  1. **필터링**: 조건을 못 맞추는 노드를 뺍니다(CPU·메모리 requests, nodeSelector·nodeAffinity, taint/toleration 등).
  2. **점수 매기기**: 남은 노드에 점수를 매겨(남는 자원, 고르게 분산 등) 가장 높은 노드에 바인딩합니다.
- 예: CPU 10개를 요청한 Pod 라면 10개를 줄 수 없는 노드는 탈락하고, 배치한 뒤 남는 CPU 가 더 많은 노드가 높은 점수를 받습니다.
- 다른 스케줄러를 쓰려면 Pod 의 `spec.schedulerName`(Day 5), 스케줄러 없이 직접 배치하려면 `spec.nodeName`(Day 3)을 씁니다.
- kubeadm: `/etc/kubernetes/manifests/kube-scheduler.yaml`

> ⚠️ **최신 버전**: 강의 예시의 `k8s.gcr.io` 이미지는 `registry.k8s.io` 로 바뀌었고, 스케줄러의 `--address` 플래그는 없어졌습니다(지금은 `--bind-address`).

### kube-controller-manager

- **컨트롤러**는 "감시 → 원하는 상태와 현재 상태 비교 → 차이를 메우는 조치"를 끝없이 반복하는 루프입니다. 이것을 reconcile 이라고 부릅니다.
- 컨트롤러는 논리적으로 각각 별개지만, 하나의 바이너리·프로세스로 묶어서 실행합니다. 예: Node, ReplicaSet, Deployment, Job, EndpointSlice, ServiceAccount, Namespace, PV 바인딩, CSR 서명.
- `--controllers` 로 켜고 끕니다. `*` 는 기본 컨트롤러 전부, `-이름` 은 끄기입니다.
- kubeadm: `/etc/kubernetes/manifests/kube-controller-manager.yaml`

노드가 응답하지 않을 때의 타이밍(v1.37 공식 문서 기준):

| 항목 | 기본값 | 의미 |
| --- | --- | --- |
| `--node-monitor-period` | 5초 | Node 컨트롤러가 노드 상태를 확인하는 주기 |
| `--node-monitor-grace-period` | 50초 | 하트비트가 끊긴 뒤 노드를 NotReady(Unknown)로 바꾸기까지 |
| 자동 toleration 의 `tolerationSeconds` | 300초 | NotReady·Unreachable 노드의 Pod 를 내보내기까지 (5분) |

> ⚠️ **최신 버전**: 강의의 `--node-monitor-grace-period` 40초와 `--pod-eviction-timeout`(5분)은 예전 기준입니다. 지금 기본값은 50초이고 `--pod-eviction-timeout` 플래그는 없어졌습니다. 대신 문제가 생긴 노드에 `node.kubernetes.io/not-ready`·`node.kubernetes.io/unreachable` taint 가 붙고, Pod 에 자동으로 들어가는 toleration(`tolerationSeconds: 300`)이 끝나면 Pod 가 내보내집니다.

### cloud-controller-manager

- 클라우드 API 와 연동하는 컨트롤러 모음입니다(노드가 클라우드에서 삭제됐는지 확인, 라우트 설정, LoadBalancer Service 생성).
- 온프레미스나 Killercoda 같은 kubeadm 실습 환경에는 없습니다.

## 3. 워커 노드 구성요소

### kubelet

- 노드의 선장입니다. 노드를 API 서버에 **등록**하고, 자기 노드에 배정된 Pod 를 CRI 로 **실행**하고, 프로브를 돌리고, 노드와 Pod 상태를 **보고**합니다.
- 하트비트는 노드 상태 업데이트와 `kube-node-lease` 네임스페이스의 Lease 객체 갱신, 두 가지입니다.
- Kubernetes 가 만들지 않은 컨테이너는 관리하지 않습니다.
- **kubeadm 은 kubelet 을 설치해 주지 않습니다.** 노드마다 패키지로 설치하고 systemd 서비스로 실행합니다. 그래서 `kubectl get pods -n kube-system` 에 kubelet 은 보이지 않습니다.

| kubeadm 클러스터의 kubelet 관련 파일 | 내용 |
| --- | --- |
| `/var/lib/kubelet/config.yaml` | kubelet 설정(KubeletConfiguration): `staticPodPath`, `cgroupDriver`, `clusterDNS` 등 |
| `/etc/kubernetes/kubelet.conf` | API 서버에 접속할 때 쓰는 kubeconfig (kubelet 인증서) |
| `/var/lib/kubelet/kubeadm-flags.env` | kubeadm 이 넣은 노드별 실행 플래그 |
| `/usr/lib/systemd/system/kubelet.service.d/10-kubeadm.conf` | 위 파일들을 kubelet 에 연결하는 systemd 설정 (배포판에 따라 `/etc/systemd/system/` 아래) |

```bash
systemctl status kubelet       # 실행 중인지
journalctl -u kubelet -f       # 로그 (노드가 NotReady 일 때 원인 찾기)
ps aux | grep kubelet          # 실제 실행 플래그 (--config 경로 확인)
```

> ⚠️ **최신 버전**: 강의의 systemd 예시에 있는 `--container-runtime=remote`, `--network-plugin=cni` 같은 플래그는 이제 없습니다. 런타임 소켓은 `--container-runtime-endpoint` 플래그나 설정 파일의 `containerRuntimeEndpoint` 로 지정합니다.

### kube-proxy

- Service 는 프로세스도 네트워크 인터페이스도 없는 **가상 IP** 입니다. 각 노드의 kube-proxy 가 Service 와 EndpointSlice 를 지켜보다가 "Service IP:포트 → Pod IP:포트" 전달 규칙을 커널에 설치합니다.
- kubeadm 에서는 DaemonSet(노드마다 1개)이고, 설정은 `kube-system` 네임스페이스의 ConfigMap `kube-proxy` 에 있습니다.
- Service 전달을 직접 구현하는 네트워크 플러그인(CNI)을 쓰면 kube-proxy 가 없어도 됩니다. 그래서 공식 문서에서는 "선택" 구성요소로 분류합니다.

| 리눅스 모드 | v1.37 기준 상태 |
| --- | --- |
| `iptables` | 기본값 (모드를 지정하지 않으면 이것) |
| `nftables` | 사용 가능, 앞으로 기본값이 될 예정 |
| `ipvs` | v1.35 부터 deprecated. v1.40 부터 기본 비활성, v1.43 에서 제거 예정 |

```bash
kubectl -n kube-system get daemonset kube-proxy
kubectl -n kube-system get configmap kube-proxy -o yaml | grep mode
```

> ⚠️ **최신 버전**: 강의 표의 `userspace` 모드는 이미 제거됐고, `eBPF` 는 kube-proxy 의 모드가 아니라 Cilium 같은 CNI 가 kube-proxy 를 대신하는 방식입니다.

### 컨테이너 런타임과 CRI

- kubelet 과 런타임은 **CRI**(Container Runtime Interface, gRPC 프로토콜)로 통신합니다. CRI 를 구현한 런타임이면 containerd, CRI-O 등 무엇이든 쓸 수 있습니다.
- v1.26 부터는 런타임이 CRI `v1` API 를 지원해야 kubelet 이 노드를 등록합니다.
- containerd 의 소켓은 보통 `unix:///var/run/containerd/containerd.sock` 입니다.

## 4. Docker, containerd, 그리고 CLI 세 가지

- 처음 Kubernetes 는 Docker 전용이었습니다. 여러 런타임을 지원하려고 **CRI** 가 생겼는데 Docker 는 CRI 를 구현하지 않아 **dockershim** 이라는 중간 다리로 연결했습니다.
- **v1.24 에서 dockershim 이 제거**되면서 Docker Engine 을 노드 런타임으로 바로 쓰는 방식은 끝났습니다.
- 그래도 **Docker 로 빌드한 이미지는 그대로 실행됩니다.** 이미지가 OCI 표준을 따르기 때문입니다. 로컬에서 `docker build` 한 애플리케이션 이미지도 containerd 노드에서 문제없이 실행됩니다.
- OCI 표준은 이미지 형식(image spec)과 런타임 동작(runtime spec) 두 가지입니다.
- containerd 는 Docker 에서 분리된 CNCF 졸업 프로젝트로, CRI 를 지원해서 Kubernetes 가 Docker 없이 바로 씁니다.

| CLI | 만든 곳 | 용도 | CKA 에서 |
| --- | --- | --- | --- |
| `ctr` | containerd 에 포함 | containerd 저수준 디버깅 | 거의 안 씀 |
| `nerdctl` | containerd 하위 프로젝트 | Docker 와 같은 사용감 (`docker` → `nerdctl`) | 안 씀 |
| `crictl` | Kubernetes (cri-tools) | CRI 런타임의 Pod·컨테이너 점검 | **필수** |

| Docker | crictl | 비고 |
| --- | --- | --- |
| `docker ps` | `crictl ps` | `-a` 를 붙이면 종료된 컨테이너까지 |
| — | `crictl pods` | Pod 샌드박스 목록 (`--name`, `--label` 로 거르기) |
| `docker logs` | `crictl logs` | `--tail N`. stdout 과 stderr 를 나눠서 출력 |
| `docker exec -it` | `crictl exec -it` | |
| `docker images` | `crictl images` | |
| `docker inspect` | `crictl inspect` | |

- crictl 의 접속 설정은 `/etc/crictl.yaml` 에 있습니다(`runtime-endpoint: unix:///var/run/containerd/containerd.sock`).
- crictl 은 **보는 도구**입니다. crictl 로 Pod 밖에서 만든 컨테이너는 kubelet 이 모르는 것이라 정리될 수 있습니다. 반대로 `crictl stop` 으로 static Pod 의 컨테이너를 멈추면 kubelet 이 곧 다시 띄웁니다.

## 5. Pod 와 YAML

- Pod 는 Kubernetes 에서 만들 수 있는 **가장 작은 배포 단위**입니다. 컨테이너를 직접 스케줄하지 않고 Pod 로 감싸서 다룹니다.
- 보통 **Pod 하나에 컨테이너 하나**입니다. 사용자가 늘면 컨테이너를 추가하는 게 아니라 **Pod 를 더 만듭니다**(scale out).
- 컨테이너 여러 개를 한 Pod 에 넣는 것은 꼭 붙어 다녀야 할 때만입니다(로그 수집, 프록시 같은 사이드카, Day 10). 같은 Pod 의 컨테이너는
  - 같은 노드에서 함께 생성되고 함께 종료되며
  - 네트워크 네임스페이스를 공유해 IP 가 같고 `localhost` 로 서로 접속하며(포트 공간도 공유)
  - 볼륨을 함께 쓸 수 있습니다.
- 실무에서는 Pod 를 직접 만들기보다 Deployment 같은 워크로드 리소스로 만듭니다(Day 2). 하지만 시험에는 Pod 를 직접 다루는 문제도 많이 나옵니다.

### Pod YAML 의 뼈대

| 최상위 필드 | 내용 | Pod 의 예 |
| --- | --- | --- |
| `apiVersion` | API 그룹과 버전 | `v1` |
| `kind` | 리소스 종류 | `Pod` |
| `metadata` | 이름, 네임스페이스, 라벨, 어노테이션 | `name: web` |
| `spec` | 원하는 상태 (Pod 는 `containers` 목록 등) | `containers: [...]` |

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: myapp-pod
  labels:              # name 과 같은 들여쓰기(형제)
    app: myapp
    tier: frontend
spec:
  containers:          # 리스트라서 항목마다 "-"
  - name: nginx
    image: nginx:1.29-alpine
    ports:
    - containerPort: 80
```

| 리소스 | apiVersion |
| --- | --- |
| Pod, Service, ConfigMap, Secret, Namespace | `v1` |
| ReplicaSet, Deployment, DaemonSet, StatefulSet | `apps/v1` |
| 모를 때 | `kubectl api-resources` 의 APIVERSION 열 |

- YAML 을 처음부터 손으로 쓰지 마세요. `kubectl run web --image=nginx --dry-run=client -o yaml > web.yaml` 로 뼈대를 만들고 고칩니다.
- 필드 이름이 기억나지 않으면 `kubectl explain pod.spec.containers` 로 찾습니다. 하위 필드 전체는 `--recursive` 를 붙입니다.

> ⚠️ **최신 버전**: kubectl 1.18 부터 `kubectl run` 은 항상 Pod 만 만듭니다. 강의에 나오는 `--restart=Never` 는 Pod 를 만들기 위한 옵션이 아니라 `restartPolicy` 를 `Never` 로 바꾸는 옵션입니다.

### 실행 중인 Pod 에서 바꿀 수 있는 것

공식 문서 기준으로 실행 중인 Pod 의 `spec` 에서 바꿀 수 있는 필드는 다음뿐입니다.

- `spec.containers[*].image`, `spec.initContainers[*].image`
- `spec.activeDeadlineSeconds`, `spec.terminationGracePeriodSeconds`
- `spec.tolerations`(추가만 가능), `spec.schedulingGates`

라벨과 어노테이션은 `kubectl label`, `kubectl annotate` 로 바꿀 수 있지만 `name`, `namespace` 는 바꿀 수 없습니다. CPU·메모리는 v1.35 부터 정식 기능이 된 in-place resize 로 `resize` 서브리소스를 통해서만 바꿉니다(Day 11). 그 밖의 필드(포트, 환경 변수, 볼륨 등)는 **지우고 다시 만들어야** 합니다.

```bash
kubectl get pod web -o yaml > web.yaml   # kubectl edit 이 거부되면 /tmp/kubectl-edit-*.yaml 에 저장됨
vi web.yaml
kubectl replace --force -f web.yaml      # 지우고 같은 이름으로 다시 생성
```

## 6. static Pod

- kubelet 이 API 서버 없이 **노드의 디렉터리를 직접 읽어서** 띄우는 Pod 입니다. kubeadm 은 컨트롤 플레인 4종(etcd, kube-apiserver, kube-controller-manager, kube-scheduler)을 static Pod 로 띄웁니다.
- 디렉터리는 kubelet 설정의 `staticPodPath` 이고, kubeadm 기본값은 `/etc/kubernetes/manifests` 입니다. 찾는 순서는 `ps aux | grep kubelet` → `--config` 파일 → `grep staticPodPath` 입니다.
- kubelet 이 이 디렉터리를 주기적으로 살펴서 파일이 생기면 Pod 를 만들고, 고치면 다시 만들고, 없어지면 지웁니다.
- API 서버에는 **미러 Pod** 로 보입니다. 이름은 `<Pod이름>-<노드이름>`(예: `kube-apiserver-controlplane`)이고, 소유자(`ownerReferences`)는 `Node` 이며, 라벨도 그대로 따라옵니다.
- `kubectl delete` 로 미러 Pod 를 지워도 kubelet 은 static Pod 를 계속 실행하므로 곧 다시 보입니다. 정말 없애려면 **매니페스트 파일을 지웁니다.**
- 다른 노드(예: node01)에 static Pod 를 만들려면 `ssh node01` 로 접속해서 그 노드 kubelet 의 `staticPodPath` 를 확인하고 그 디렉터리에 파일을 둡니다.

> ⚠️ **공식 문서의 주의 사항**: kubelet 은 `.` 으로 시작하지 않는 **모든 파일**을 확장자와 상관없이 읽습니다. `cp kube-apiserver.yaml kube-apiserver.yaml.bak` 처럼 같은 디렉터리에 백업을 두면 백업까지 static Pod 로 읽혀서 예전 설정이 적용될 수 있습니다. **백업은 반드시 디렉터리 밖에**(예: `/etc/kubernetes/backup/`, `/root/`) 두세요. 시험에서 API 서버 매니페스트를 고치기 전에 특히 중요합니다.

## 🎯 시험 포인트

1. 컨트롤 플레인이 이상하면 **`/etc/kubernetes/manifests/` 부터** 봅니다. 고친 뒤에는 kubelet 이 다시 띄울 때까지 잠시 기다리고, `kubectl` 이 안 되면 `crictl ps -a`, `crictl logs` 로 확인합니다.
2. **kubelet 은 Pod 가 아닙니다.** `systemctl status kubelet`, `journalctl -u kubelet` 으로 봅니다.
3. 매니페스트 **백업은 디렉터리 밖**에 둡니다.
4. 실행 중인 Pod 는 이미지 말고는 대부분 못 바꿉니다. YAML 로 받아 고친 뒤 `kubectl replace --force -f` 로 다시 만듭니다.
5. 출력을 파일로 저장하는 문제는 jsonpath·custom-columns 로 정확히 뽑고, 저장한 뒤 `cat` 으로 확인합니다.
6. YAML 은 `--dry-run=client -o yaml` 로 만들고, 필드는 `kubectl explain` 으로 찾습니다.

## ✅ 스스로 점검

<details>
<summary>Q1. 새로 만든 Pod 가 계속 Pending 이고 노드도 비어 있으며 Events 도 없습니다. 어떤 구성요소를 먼저 의심해야 할까요?</summary>

**kube-scheduler** 입니다. 노드를 골라 줄 스케줄러가 없으니 `spec.nodeName` 이 비어 있고, 스케줄링 이벤트도 남지 않습니다. `kubectl -n kube-system get pods` 로 스케줄러 Pod 상태를 보고 `/etc/kubernetes/manifests/kube-scheduler.yaml` 을 확인합니다.

</details>

<details>
<summary>Q2. kubectl get pods -n kube-system 에 kubelet 이 보이지 않는 이유는?</summary>

kubelet 은 Pod 가 아니라 **각 노드의 systemd 서비스**이기 때문입니다. kubeadm 도 kubelet 을 설치하지 않고, 노드마다 미리 설치해 둔 kubelet 을 씁니다.

</details>

<details>
<summary>Q3. 컨트롤 플레인 구성요소 중 etcd 에 직접 접근하는 것은?</summary>

**kube-apiserver 하나뿐**입니다. 스케줄러, 컨트롤러 매니저, kubelet 은 모두 API 서버를 거쳐서 상태를 읽고 씁니다.

</details>

<details>
<summary>Q4. kubectl -n kube-system delete pod kube-scheduler-controlplane 을 실행하면 어떻게 될까요?</summary>

API 서버에 보이는 **미러 Pod** 만 지워지고, kubelet 은 static Pod 를 계속 실행하므로 곧 다시 나타납니다. 정말 멈추려면 `/etc/kubernetes/manifests/kube-scheduler.yaml` 파일을 디렉터리 밖으로 옮겨야 합니다.

</details>

<details>
<summary>Q5. kube-apiserver.yaml 을 고치기 전에 같은 폴더에 kube-apiserver.yaml.bak 으로 백업했습니다. 무엇이 문제일까요?</summary>

kubelet 은 확장자와 상관없이 `.` 으로 시작하지 않는 모든 파일을 static Pod 로 읽습니다. 백업 파일도 같은 이름의 Pod 를 정의하므로 어느 설정이 적용될지 알 수 없고, 예전 설정이 적용될 수도 있습니다. 백업은 디렉터리 밖에 둡니다.

</details>

<details>
<summary>Q6. 실행 중인 Pod 의 containerPort 를 바꾸려면 어떻게 하나요?</summary>

포트는 실행 중에 바꿀 수 없는 필드입니다. `kubectl get pod <이름> -o yaml > p.yaml` 로 받아 고친 뒤 `kubectl replace --force -f p.yaml` 로 지우고 다시 만듭니다. `kubectl edit` 이 거부되면 `/tmp/kubectl-edit-*.yaml` 에 저장된 파일을 써도 됩니다.

</details>
